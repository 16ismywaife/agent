# D3 · 多轮对话与历史管理

> 实验时间：2026-10-06
> 模型：`deepseek-flash`（思考模式已关闭）
> 脚本：`week3/day1.py` → `d3_multi()`，命令 `python week3\day1.py --only 3`
> 数据：`usage` 里的数字都是**实测输出**。

---

## 一、核心认知：模型没有记忆

**每一次 API 请求都是独立的一次计算。模型不记得上一句 —— 是「你把历史全传回去了」。**

所以"多轮对话"这件事，在代码里其实只有一句话：

> **你每次都要把从开头到现在的全部消息，重新发一遍。**

### 代码结构（三步）

```python
history = [{"role": "system", "content": "你是一个耐心的 Python 助手。"}]

for q in questions:
    history.append({"role": "user", "content": q})        # ① 把问题加进去
    txt, usage = ask(client, model, history)              # ② 传【整个】history
    history.append({"role": "assistant", "content": txt}) # ③ 把回复也加回去
```

**① 和 ② 是显然的（不写就报错）。③ 才是关键，而且它漏了不会报错** —— 见第四节。

---

## 二、为什么这三个问题能验证对错

`d3_multi` 里的三个问题带**指代词**：

| 问题 | 指代什么 |
|---|---|
| 什么是列表推导式？ | 无指代，可独立回答 |
| **它**和 map 有什么区别？ | **"它" = 列表推导式**（上一轮的内容） |
| **那**什么时候该用**哪个**？ | **"哪个" = 列表推导式 vs map**（同上） |

**所以第 2、3 问在孤立状态下物理上答不出来。** 实测孤立提问「它和 map 有什么区别？」：

> 你问的"它"我不确定具体指哪个，但最常见的对比是 **`forEach` 和 `map`**。

**猜错了**（猜成了 JavaScript）。这是**自带的验证机制** —— 写错了不用别人告诉你，输出自己会暴露。

---

## 三、token 数据是更硬的证据

光看"答得对"不够（模型可能猜对）。**`prompt_tokens` 的递增才是铁证**：

| 轮次 | `prompt_tokens` | `completion_tokens` | `total` | 说明 |
|---|---|---|---|---|
| 第 1 轮 | **25** | **87** | 112 | 只有 system + 当前问题 |
| 第 2 轮 | **120** | **62** | 182 | ↑ 多出的 95 ≈ 第 1 轮的全部内容 |
| 第 3 轮 | **190** | **61** | 251 | ↑ 继续累积 |

**算术关系完全自洽**，这就是"历史被完整传回去了"的数学证明：

```
轮1:  prompt 25  + completion 87  = total 112  ✅
轮2:  prompt 120 + completion 62  = total 182  ✅
轮3:  prompt 190 + completion 61  = total 251  ✅

轮1 total 112  →  轮2 prompt 120    差 +8  ← 新问题「它和map有什么区别」的 token 数
轮2 total 182  →  轮3 prompt 190    差 +8  ← 新问题「那什么时候用哪个」的 token 数
```

**"下一轮的 prompt = 上一轮的完整内容 + 新问题"** —— 没有多余的、也没有漏掉的。
**这比"它答得对"硬得多。**

> **★ 这个技巧以后一直有用**：A/B 对比时，先看 `prompt_tokens` 差多少，
> 就知道"你以为改的变量，是不是真的改到了"。
> （D2 那次标签错位，也是靠 token 数发现的）

### 关于缓存

第一次跑（无长度约束）时，第 3 轮出现过 `prompt_cache_hit_tokens=768` ——
**重复发送的历史前缀会被厂商缓存**，同样的前缀不用重复计费。

但要注意：**缓存省钱，不省"你必须自己传历史"这件事。** 而且加上长度约束后，
历史变短了，缓存自然也就没什么可命中的了（实测三次都是 0）。

## 四、★ 我踩的坑：`role` 写成了 `system`

**第一次写的时候，我把模型回复的 role 写成了 `system`：**

```python
history.append({"role": "system", "content": txt})    # ❌ txt 是模型的回复
```

**而且它没报错，答案还是对的。**

原因：消息序列实际长这样 ——

```
[0] system      你是一个耐心的 Python 助手      ← 真正的人设
[1] user        什么是列表推导式
[2] system      列表推导式是…（模型的回复）      ← ★ 这里错了
[3] user        它和 map 有什么区别
[4] system      列表推导式…（模型的回复）
[5] user        那什么时候用哪个
```

**模型逐条读消息，读到内容就能理解** —— 所以"它""哪个"还是猜对了。**答案对，但 role 是错的。**

### 为什么这是真错误

`role` 不是装饰，它告诉模型**"这句话是谁说的"**：

| role | 含义 |
|---|---|
| `system` | **规则 / 人设**，平台方（开发者）的指示 |
| `user` | 用户说的话 |
| **`assistant`** | **模型自己之前说过的话** |

**写成 `system`，等于把模型的输出变成了"给模型自己的命令"。** 后果：

1. **语义错位** —— 模型的回复被当成规则
2. **`system` 出现在对话中间是非标准用法**，某些厂商/模型会行为异常
3. **一致性变差** —— 模型会更倾向重复它"作为 system 声明过"的内容
4. **Week4 做 Agent 时多轮工具调用会彻底乱掉**

改法：

```python
history.append({"role": "assistant", "content": txt})   # ✅
```

> **★ 这个坑的教训和 D2 那次一样**：**代码没报错、结果也看着对，但其实是错的。**
> 判断依据不能只看"输出像不像对的"，要看**数据结构是否符合语义**。
> 这次的抓手就是 role 列表 —— 一个对话里应该有且仅有 **1 个 system**。

## 五、history 无限增长 = 上下文管理问题的来源

每轮往 history 加 2 条（user + assistant），长度是：

```
第 1 轮后：3 条
第 2 轮后：5 条
第 3 轮后：7 条
...
第 N 轮后：1 + 2N 条
```

**而每次请求都要把整个 history 发出去。** 所以：

| 问题 | 后果 |
|---|---|
| 历史越来越长 | `prompt_tokens` 变大 → **成本上升**（实测 14 → 796 → 1913） |
| 超过模型上下文上限 | **直接报错** |
| 上下文太长 | 模型注意力被稀释，**效果反而下降** |

**这就是 Agent 领域说的「上下文管理」。** 常见处理：只保留最近 N 轮 / 把旧对话总结成一段 / 丢弃无关内容。

**Week4 做 Agent 时会正面撞上这个问题** —— 因为 Agent 每调一次工具就会多两条消息，增长比聊天快得多。

## 六、顺便验证的：system 里的"输出契约"（length 约束）

D2 的结论是「system 定义的是**输出契约**，不是人设」。D3 里正好有个新场景可以验证。

### 6.1 改动前后（实测）

**没加长度约束时**（第一次跑）：

| 轮次 | `completion_tokens` | 末轮回答长度 |
|---|---|---|
| 第 1 问 | **776** | — |
| 第 2 问 | **1111** | — |

**加了约束之后**（system 改成「…每次回答控制在 3 句话以内」）：

| 轮次 | `completion_tokens` | `prompt_tokens` | 末轮回答长度 |
|---|---|---|---|
| 第 1 问 | **87** | 25 | — |
| 第 2 问 | **62** | 120 | — |
| 第 3 问 | **61** | 190 | 93 字 |

**结论：`completion_tokens` 降了 89~94%。**

### 6.2 但"改动前后"不是干净的对照 —— 补做了对照实验

**问题**：改动前后各跑一次，中间变量太多（模型本身的随机性、历史长度也在变）。
所以另做了一次**同一组问题、只改 system** 的对照（脚本：`week3/_diag_length_contract.py`）：

| | 无长度约束 | 有长度约束 | 降幅 |
|---|---|---|---|
| `completion_tokens` 逐轮 | **899 / 1496 / 1172** | **86 / 65 / 61** | **−94%** |
| `prompt_tokens` 逐轮 | 15 / **922** / **2426** | 25 / 119 / 192 | 末轮 **−92%** |
| 末轮回答长度 | **2483 字** | **93 字** | — |

无约束那次的末轮回答是「一张决策流程图 + 场景对照表 + 典型例子 + 一句话决策规则」。

### 6.3 ★ 但要分清「直接效果」和「连锁效应」

**第 2、3 轮的差异，主因不是契约本身，而是它引起的连锁：**

```
第 1 轮输出长  →  第 2 轮输入长  →  第 2 轮输出也更容易长  →  越往后差得越多
```

| | 输入是否相同 | 差异来源 |
|---|---|---|
| **第 1 轮** | 几乎相同（只差 system 那十几个字） | **输出契约的直接效力**：`899 → 86` |
| **第 2、3 轮** | 差很多（上一轮输出长度不同） | **连锁效应**为主 |

**诚实的结论**：输出契约不只省当次的钱，**它还省后面每一次的钱** —— 因为历史短了。
这是"输出契约的复利"。

### 6.4 和 D4 的关系

**"3 句话以内"是【软约束】—— 模型听了，但那是它愿意听。**
D4 用的是 **API 层面强制**（`response_format={"type": "json_object"}`），
模型**没有不听的选项**。

**软约束 → 硬约束，这就是 D4 要跨的那一步。**

## 七、已知局限

1. **只测到 3 轮**，没测长对话（10 轮以上）时 `prompt_tokens` 的增速。
   按当前增速（每轮 +8 token 的新问题 + 上一轮全部内容），推算 20 轮左右会到什么量级 —— 没实测。
2. **没测历史截断方案** —— "只保留最近 N 轮"具体怎么实现、效果如何，没做。
   （这是 Week4 会正面撞上的问题）
3. **对照实验只跑了 1 次** —— n=1。虽然两组的差距是 10 倍量级，方向上不会错，
   但**按 D2 的教训，严格结论应该 n≥5 看分布**。这里的数字当"量级参考"，不当精确值。
4. **`turns` 参数没实际使用** —— 函数签名里有，但代码直接遍历了整个 `questions`。
   要么用它（`questions[:turns]`），要么删掉，别留一个会让人困惑的无用参数。
5. **只测了一个模型**（`deepseek-flash`），换模型"3 句话以内"是否仍有效，未知。
