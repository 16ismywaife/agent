## 实验设计

**改的变量**：messages 里有没有 `system` 消息。

**保持不变**：模型、`temperature`（默认）、`max_tokens`（默认）、`user` 内容、调用次数。

| 组 | messages 结构 |
|---|---|
| **无 system** | `[{"role": "user", "content": SENT}]` |
| **有 system** | `[{"role": "system", "content": SYS}, {"role": "user", "content": SENT}]` |

```
SENT = "把这句话改得更正式：这个方案我觉得不太行"
SYS  = "你是一名严谨的技术文档编辑。把句子改写得更正式（书面、用于工作场合），只输出改写后的句子。"
```

**每组跑 5 次**（n=5），共 10 次调用。

## 统计量

| 指标 | 无 system | 有 system | 倍数 |
|---|---|---|---|
| 最小 / 最大字数 | 14 / **477** | 18 / 30 | — |
| 极差 | **463** | 12 | **38.6×** |
| 均值 | 111.8 | 25.4 | 4.4× |
| 中位数 | 22.0 | 28.0 | — |
| 标准差 | 204.2 | 5.5 | 36.8× |
| **变异系数 CV**（标准差/均值） | **1.83** | **0.22** | **8.3×** |
| 输出 > 100 字（给了菜单） | **1 / 5** | 0 / 5 | — |
| 以「经过」开头 | 0 / 5 | **5 / 5** | — |

> **为什么用变异系数（CV）而不是标准差做主要指标**：
> 两组的**均值本身就差 4.4 倍**，标准差之比会被均值差异放大。
> CV 是"相对于自身均值"的波动，才是纯粹的稳定性度量。
> 顺带一提：477 那个值把标准差抬得很高，所以更要看 CV。

## 结论

### 1. system 的作用不是"设定人设"，而是**约束输出形状**

拆开那条 system：

```
你是一名严谨的技术文档编辑。              ← 身份。影响最小
把句子改写得更正式（书面、用于工作场合），
只输出改写后的句子。                       ← ★ 决定性的半句
```

**真正起作用的是「只输出改写后的句子」这个约束，不是「严谨技术文档编辑」这个身份。**

没有它的时候，模型把 `"把这句话改得更正式：…"` 理解成
**"帮我想想有哪些更正式的说法"** → 给出一个**菜单**（5 个版本 + 要点总结）。

有它之后，任务被收窄成 **"给出那一句改写"** → 只给一句。

**这条命令的语义是：**
> **system 定义的是「输出契约」（output contract），不是「语气」。**

### 2. 一致性比单条质量重要 —— 而且这是能不能写代码的问题

看无 system 的第 2 条：`对于这个方案，我持保留意见。`（14 字）

**单看这一条，它和第 1 条一样好，甚至更简洁。** 问题不在质量，在于：

> **你不知道下一次会拿到什么。** 一次 477 字的菜单，一次 14 字的句子。

如果要把这个调用接进程序（Week4 的 Agent 就是）：

```python
reply = ask(...)      # 这次可能是 "该方案尚不可行。"
                      # 下次可能是 "**1. 标准职场版**\n> …\n\n**改写要点总结**…"
# 下一行没法写 —— 因为不知道拿到的是什么结构
```

**有 system 时，5 次全部落在 18~30 字、全部单句、全部以「经过」开头。**
这才是一个下游代码能依赖的输出。

**所以 D2 和 D4「结构化输出」是同一件事的两面**：
都是在给模型输出**定形**，让程序能处理。

### 3. 一个更细的观察：「经过」这个词被 system 稳定带出来了

有 system 时 **5/5** 以「经过」开头，无 system 时 **0/5**。

这不是巧合 —— 「书面、用于工作场合」这个描述把"公文体"的措辞偏好也一起带进来了。
**说明 system 除了约束结构，确实也在塑造用词风格。** 只是"结构"的影响远大于"风格"。

## ★ 实验过程中的一次错误结论（这条要留着）

**第一轮我只跑了 2 次（每组各 1 次），得出的结论是反的。**

| 轮次 | 样本量 | 当时的结论 |
|---|---|---|
| 第 1 轮 | n=1 | 「system 让输出变得更随意了」 |
| 第 2 轮 | n=1（改了提示词） | 「system 让它开始解释发挥，帮倒忙」 |
| **第 3 轮** | **n=5** | **「system 显著降低输出变异性」** |

**为什么前两轮错了**：n=1 时抽到的恰好是"短句"那一边，
而这类任务**本来就有一半概率给菜单、一半概率给单句**（实测 5 次里 1 次给菜单）。
**样本太少时，随机性会被当成变量的效果。**

**修复方式**：把样本量提到 5，同时统计**分布**而不是看单条。

> **这条比结论本身值钱。**
> 「我用 2 个样本得出一个反结论，加到 5 个样本推翻了它」——
> 这说明我知道自己的结论有多可靠。**能识别不确定性，是工程判断力的核心。**

**附带教训（同一天踩的第二次）**：同一天做 temperature 实验时也踩了同类坑 ——
那次是 `max_tokens` 设太小导致 3 次输出**全是空字符串**，
被统计成"输出相同"，差点得出「temperature 不起作用」的错误结论。
**两次都说明：先确认测量方法本身是可靠的，再下结论。**

## 已知局限（没做到的，别假装做到了）

1. **变量没完全控制干净。** `SENT` 里混了指令前缀（`把这句话改得更正式：`），
   这本身就在"邀请"模型给多个选项。
   **严格说，无 system 时输出菜单，有一部分是 prompt 措辞造成的，不全是缺 system。**
   → 补做方案：把 `SENT` 换成纯句子 `"这个方案我觉得不太行"`，再跑一组 n=5。
2. **n=5 仍然偏小。** 要下更强的结论建议 n≥20。当前结论方向明确（8.3× 的 CV 差距），
   但具体倍数不必当真。
3. **只测了一个模型**（`deepseek-flash`），换模型结论未必成立。
4. **只看字数和开头词，"一致性"是间接度量。**
   更严格的做法是算输出的语义相似度（Week5 做 RAG 时会用到向量，那时可以回头看这个）。
5. **没测 few-shot。** 本实验只对比了 system 的有无。
