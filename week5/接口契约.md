## 0. 一句话说清这个模块

> **输入**：Agent 每次调用工具的一条记录（工具名、成功与否、耗时、参数、结果）。
> **输出**：一个 SQLite 数据库文件 + 三张统计报表（成功率 / 耗时分布 / 失败详情）。

**它解决什么问题**：Week4 的 Agent 能调工具了，但**跑完就没了** ——
调了几次、哪次慢、哪次失败、失败在哪，全靠肉眼看终端。
这个模块把每次调用**落盘**，之后用 SQL 回答"我的 Agent 到底哪儿不稳"。

**它在整体项目中的作用**（★ 文档考核点名的自查项）：
它是「方向 3 评测」的**可观测层**。Week4 的 `run_agent()` 只有"跑通/没跑通"，
加了这个模块之后才有**成功率、P95 耗时、失败原因**这些能写进简历的数字。
同时它顺带补掉简历上的 **SQL** 缺口（手册 4.12）。

## 1. 输入契约

### 1.1 数据来源

| 来源 | 是什么 | 谁产生 |
|---|---|---|
| **真实运行** | `week4/agent_calc.py` 里 `run_agent()` 每次执行工具时 | Agent 主循环 |
| **样本数据** | `week5/sample_records.jsonl`（手工造，用于离线演示） | 本模块自带 |

**关键设计决定：不改 `week4/agent_calc.py` 的执行逻辑。**
日志是**包在工具外面的一层**，工具本身（`calculator` / `get_time`）一行都不动。

### 1.2 一条记录有哪些字段

| 字段 | 类型 | 必填 | 说明 | 来源 |
|---|---|---|---|---|
| `tool` | TEXT | ✅ | 工具名，如 `calculator` | `tc.function.name` |
| `success` | INTEGER | ✅ | `1` 成功 / `0` 失败 | 看工具返回是不是错误文本 |
| `elapsed_ms` | REAL | ✅ | 耗时，毫秒 | 执行前后各取一次时间 |
| `ts` | TEXT | ✅ | 调用时间，**ISO8601 带时区** | 执行时刻 |
| `args` | TEXT | ◐ | 参数的 JSON 文本 | `tc.function.arguments` |
| `result` | TEXT | ◐ | 工具返回，**截断到 200 字符** | 工具返回值 |
| `error` | TEXT | ◐ | 失败时的错误信息 | 异常 / 错误文本 |

◐ = **待你确认**（见 §6 决策点 ①）。最小版只留前 4 列 —— 那就是手册 4.12 那张表。

### 1.3 调用方式（两种，任选其一）

```python
# 方式 A · 上下文管理器（推荐）：函数体不用改，缩进进去就行
with CallLogger("logs/agent.db") as lg:
    lg.record("calculator", args={"expression": "(23*7+15)/2"})   # ← 这里开始计时
    result = calculator("(23*7+15)/2")                            # ← 原本的代码，一行不动
    lg.done(result)                                               # ← 这里结束计时并落盘

# 方式 B · 一步到位（给"已经写成一个函数"的场景）
result = logged_call("calculator", calculator, expression="(23*7+15)/2")
```

> 方式 A 里 `record()` 和 `done()` 为什么要分开？因为**计时必须夹住真正执行的那一行**。
> 这也解释了为什么不写成装饰器：装饰器要改 `TOOLS_IMPL` 的注册方式，会把 Week4 的代码搅进去。

## 2. 输出契约

### 2.1 产出物清单

| 产出 | 路径 | 说明 |
|---|---|---|
| 数据库 | `logs/agent_calls.db` | SQLite 单文件；`logs/` 已在 `.gitignore`，**不入库** |
| 统计报表 | 终端表格 + `week5/report_sample.md` | 三张表（见 2.3），可复现 |

### 2.2 数据库表结构

```sql
CREATE TABLE IF NOT EXISTS calls (
    id         INTEGER PRIMARY KEY AUTOINCREMENT,   -- 每行唯一编号
    ts         TEXT    NOT NULL,                    -- ISO8601 带时区
    tool       TEXT    NOT NULL,
    success    INTEGER NOT NULL,                    -- 1 / 0
    elapsed_ms REAL    NOT NULL,
    args       TEXT,                                -- 可空
    result     TEXT,                                -- 可空，截断 200 字
    error      TEXT                                 -- 可空
);
CREATE INDEX IF NOT EXISTS idx_calls_tool  ON calls(tool);
CREATE INDEX IF NOT EXISTS idx_calls_ts    ON calls(ts);
```

> ★ **和手册 4.12 的差异（要能解释）**：
> 手册那张示例表叫 `tool_calls`，是**为了讲语法**随便起的；这里叫 `calls`，
> 且 `ts` 用**显式 ISO8601** 而不是 `DEFAULT CURRENT_TIMESTAMP` ——
> 因为 SQLite 的 `CURRENT_TIMESTAMP` 是 **UTC 且不带时区标记**，
> 报告里显示时间会和你本地时间差 8 小时，属于"看起来正常但是错的"那一类坑。

### 2.3 三张报表（SQL 要自己写）

| 报表 | 回答的问题 | 用到什么 SQL |
|---|---|---|
| **① 按工具汇总** | 每个工具调了几次、成功率多少、平均/P95 耗时 | `GROUP BY` + `COUNT` / `AVG` + `HAVING` |
| **② 慢调用 Top N** | 最慢的 10 次是哪些 | `ORDER BY ... DESC LIMIT 10` |
| **③ 失败清单** | 失败的调用，错在哪 | `WHERE success = 0` |

**① 的期望输出格式**（就是手册 4.12 那段查询的成品）：

```
tool          n    rate%   avg_ms   p95_ms
calculator    12   91.7    11.3     24.8
get_time       3   100.0    0.4      0.6
```

> **P95 怎么算**：SQLite 没有现成的百分位函数。两条路 ——
> 用 `ORDER BY elapsed_ms LIMIT 1 OFFSET (SELECT COUNT(*)*95/100 ...)`，
> 或者把耗时取回 Python 用 `statistics.quantiles()` 算。
> **★ 这个取舍你定**（见 §6 决策点 ③）。

## 6. ★ 5 个边界决策 —— 已定（2026-10-20）

> 手册 D1 要求「写接口契约，**给别人看一眼确认边界**」。
> 这 5 条是真正会返工的地方，所以一条条定死，不留"到时候再说"。

| # | 决策点 | **定了** | 为什么这么定 |
|---|---|---|---|
| ① | 存不存 `args` / `result` / `error`？ | **全存，截断 200 字** | 失败时排查要看的正是"传了什么、回了什么"。不存 = 报表③只剩一行"失败了"，等于没记 |
| ② | `success` 怎么判？ | **返回错误文本就算失败** | Week4 的 `calculator` 是**返回**错误文本（`"计算错误..."` / `"错误，含未知字符"`），不抛异常 —— 只认异常的话，所有失败都会被记成成功 |
| ③ | P95 在哪算？ | **SQL 里算**（nearest-rank） | 本模块的考核点之一是 SQL；且结果和 Python 算的一样，能用 SQL 就别多写代码 |
| ④ | 数据库连接怎么管？ | **每条记录开关一次** | 简单、崩了不丢已写数据。代价约 1ms/条，**且不计入 `elapsed_ms`**（计时只夹住工具执行那段，不是写入那段） |
| ⑤ | 要不要 `--since` 日期过滤？ | **D1~D2 不做** | 先不扩边界；D4 加统计时再一起考虑，避免"契约没定就长功能" |

**这 5 条的共同点**：每一条都在"省事"和"以后不用返工"之间选。
原则是 —— **当数据一旦丢了就补不回来（①②），就往全里存；当功能还没到用的时候（③④⑤），就选最省事的。**
