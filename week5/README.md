# Week5 · Agent 调用日志

> 给 Agent 每次调用工具记一条账（调了什么、成没成、花了多久、错在哪），
> 存进 SQLite，再用 SQL 查出「哪个工具最不稳、哪次最慢、为什么失败」。

---

## 三、输入 / 输出

### 输入

一条工具调用记录：

| 字段 | 例子 | 说明 |
|---|---|---|
| `ts` | `2026-10-23T15:45` | 调用时间 |
| `tool` | `calculator` | 工具名 |
| `success` | `1` / `0` | 成没成 |
| `elapsed_ms` | `12.4` | 耗时（毫秒） |
| `error` | `计算错误division by zero` | 失败时的错误文本（成功填 `None`） |

### 输出

**一个数据库文件**：`logs/v2.db`，里面一张表 `calls`

**三张报表**（打印到终端）：

| 报表 | 回答什么问题 | 用到的 SQL |
|---|---|---|
| ① 按工具汇总 | 每个工具调了几次、成功率、平均耗时 | `GROUP BY` + `COUNT` / `AVG` / `ROUND` |
| ② 最慢的 10 次 | 哪几次特别慢 | `ORDER BY ... DESC` + `LIMIT` |
| ③ 失败清单 | 哪些调用失败了、错在哪 | `WHERE success = 0` |

## 四、它在整体项目中的作用

**没有它的时候**：Agent 跑完只能看到最终回答，以及"这次有没有调工具、调的是哪个" ——
而且**跑完就没了**。想知道"它稳不稳、哪次特别慢、失败了几次"，只能凭印象。

**有了它之后**，多出这几样东西：

| 多了什么 | 有什么用 |
|---|---|
| 调用次数 | 哪个工具真的在用，哪个从来没被调过 |
| 成功率 | ★ 回答"稳不稳" |
| 平均耗时 | 大概多快 |
| **P95 耗时** | ★ 平均值会把最慢那次摊平（253ms vs 3800ms，差 15 倍），P95 才看得出卡顿 |
| 失败的错误原文 | 不是"失败了"，而是"错在哪" |
| 而且**全部落盘** | 能回头查、能按工具比、能跨天对比 |

**为什么这比"能跑通"值钱**：

> 面试官问"你这个 Agent 稳不稳定？"
> 没有数据 → "还行吧…"（等于不会答）
> 有数据 → "16 次调用，成功率 87.5%，P95 3.8 秒，2 次失败都是除零错误"
>
> **"能跑"是及格线，"能说清跑得怎么样"才是加分项。**

**它和 Week4 的 `run_agent()` 是什么关系**：

日志是**包在「工具执行」外面**的一层 —— 执行前记下工具名，执行后记下成功与否和耗时，
然后写进数据库。

- **改了**：在工具执行前后加了记录和计时，并把结果写入 SQLite
- **没改**：`run_agent()` 的判断逻辑、messages 维护、循环结构，**一行都没动**

> 这个区分很关键：**模型响应慢**和**工具执行慢**是两件事。
> 计时只夹住工具执行那一段，量出来的数才能归因到"是工具的问题"。
> 另外，日志是**观察者**——改了被观察的对象，测出来的就不是原来那个 Agent 了。
